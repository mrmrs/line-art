The occlusion engine needs correctness fixes before performance tuning. A maintained ln.js fork is justified, but several of the highest-impact changes belong in this app’s projection layer. The largest quality improvement would be computing visible portions of line segments, rather than deciding visibility only at regularly spaced points.

Reviewed on 14 September 2026. Upstream `master` resolves to commit [`97ea438db32a307519457f03101a393568dc11a5`](https://github.com/aweary/ln.js/commit/97ea438db32a307519457f03101a393568dc11a5), dated 21 June 2020. Its package declares 0.4.0; this app installs `@lnjs/core` 0.5.0. A recursive comparison found the upstream and installed `src/` directories identical. The diagnostics below exercise the installed executable package, not just the upstream source.

Scope: the visibility pipeline, spatial tree, boxes, transformed shapes, all primitive intersection implementations, meshes, CSG, path filtering, supporting vector/matrix operations, and the app’s projection, scene preparation, height fields, and fill BVH. This is an occlusion review, not a security or general-purpose parser audit.

The reproducible evidence is in [audit-occlusion.mjs](../scripts/audit-occlusion.mjs), with captured output in [occlusion-audit-results.txt](occlusion-audit-results.txt). Run `node scripts/audit-occlusion.mjs`. It reports **14 mismatches across 10 grouped findings**, plus an intersection-count measurement. It intentionally reports defects without failing the process; it is a diagnostic harness, not a passing correctness suite. These cases should become assertions of correct behavior as patches land. No runtime code or dependency was changed for this review.

**How the app actually renders.** `geometry-service.ts` builds and caches an ln.js scene, retrieves its world-space paths, and calls the app’s `projectPaths`. That function clips segments against the homogeneous frustum, divides them into world-space samples, asks `Scene.visible(eye, point)` about each sample, and connects consecutive visible samples. It does not call upstream `Scene.renderWithMatrix`, `ClipFilter`, or the upstream path simplifier. Those upstream shortcomings must therefore be distinguished from active app defects.

`Scene.visible` casts a normalized ray from the line sample toward the eye, asks the tree for the nearest intersection along the ray, and compares the returned distance to the distance to the eye. This assumes consistent ray distances, accurate primitive intersections, and perspective projection. Several assumptions fail.

The findings below are ordered by implementation priority. P1 means an active error that can produce incorrect exported linework; P2 means a performance opportunity, a limitation needing an explicit policy, or a defect in a currently bypassed path.

1. **Fix transformed distances first.** [TransformedShape.intersect](https://github.com/aweary/ln.js/blob/97ea438db32a307519457f03101a393568dc11a5/src/shape.ts) transforms the ray through `inverse.mulRay()`. That normalizes its transformed direction, but returns the local hit distance unchanged. The app uses this wrapper for ordinary shapes, imported meshes, and transformed grids. Both uniform and nonuniform scaling are affected; incorrect distances also invalidate tree traversal comparisons.

   A minimal compatible fix keeps the normalized local ray, measures `k = length(inverseLinear * worldDirection)`, and returns `worldT = localT / k`. Preserve misses without dividing the finite `NoHit` sentinel, reject singular transforms, and avoid mutating shared hit objects. An alternative is preserving unnormalized ray parameterization everywhere, but that requires fixing kernels such as `Sphere.intersect`, which currently assumes a unit direction. Simply removing normalization would introduce another bug. Test scaling up/down, nonuniform and negative scale, nested instances, and blockers on both sides of the eye.

2. **Give visibility a camera-aware ray contract.** The app selects an orthographic projection matrix but passes the same eye-based visibility query as perspective views. Orthographic queries must use parallel directions toward the camera, with per-point ray endpoints on the selected camera boundary. For perspective, use the direction toward the eye. Define whether geometry between the near plane and eye can occlude: matching clipped rendering usually means ending queries at the near plane. Bound queries consistently; do not treat orthographic rays as infinite in one path and finite in another. This fix belongs in the app even if the dependency is forked.

3. **Make primitive surface semantics explicit.** [Cylinder](https://github.com/aweary/ln.js/blob/97ea438db32a307519457f03101a393568dc11a5/src/cylinder.ts) tests only the curved wall; [Cone](https://github.com/aweary/ln.js/blob/97ea438db32a307519457f03101a393568dc11a5/src/cone.ts) omits its base. If these represent closed solids, caps must participate in occlusion even when their outlines are not drawn. Add cap tests, handle zero quadratic coefficients and tangent cases, and choose the nearest valid hit across wall and caps. If open tubes are desirable, expose open/closed geometry explicitly. This is a modeling-policy choice in upstream, but closed-solid behavior is the useful default for this app’s solid shapes.

4. **Centralize robust ray intervals.** [Box.intersect](https://github.com/aweary/ln.js/blob/97ea438db32a307519457f03101a393568dc11a5/src/box.ts) and `Cube.intersect` divide by each ray direction component. On a parallel boundary ray, `0/0` produces NaN. The existing app [BVH slab test](../src/lib/bvh.ts) already handles zero directions explicitly; bring equivalent handling into the library. Reuse a single interval implementation instead of maintaining divergent box/cube versions. Apply the same care to kd-tree split-plane rays, including origins exactly on the split plane. The harness confirms the box/cube failure; it does not yet prove a separate kd-tree split-plane failure.

5. **Repair CSG as a subsystem.** [BooleanShape.intersect](https://github.com/aweary/ln.js/blob/97ea438db32a307519457f03101a393568dc11a5/src/csg.ts) recursively advances its ray origin by `hit.t + 0.01`, then returns a later hit without restoring the traveled distance. `Union` exists in the enum and app controls but has no containment implementation. `contains` overwrites the caller’s tolerance; `compile` does not compile children. `Cone.contains` and `Mesh.contains` always return false, so adding a union branch alone cannot make arbitrary app booleans reliable.

   First fix the missing union branch, child compilation, and accumulated distances, while adding a bounded iterative traversal. Then implement ordered boundary events for supported closed solids: sort entry/exit events, track operand membership, and return intervals where the Boolean expression is true. This avoids repeatedly stepping past thin features by a hard-coded distance. Mesh booleans need a valid closed-mesh containment policy; open/nonmanifold imports should not silently pretend to be solids. Test all three operations, coincident surfaces, small gaps, nested booleans, and rays starting inside either operand.

6. **Replace unrelated magic epsilons with a numerical policy.** Sphere discards hits within 0.01 units; cube uses 0.001; triangle uses 1e-9 for both determinant rejection and near-hit rejection. These quantities have different units and conditioning. The small-sphere and small-triangle misses are deterministic, not speculative floating-point artifacts. The app’s separate triangle BVH also has fixed determinant and distance cutoffs.

   Use explicit `tMin`/`tMax` query bounds, conservative bounds arithmetic, and tolerances derived from computation/geometry scale. Carry source primitive identity and surface information with generated marks. Suppress only the originating surface contact within its numerical error interval; do not ignore the entire host mesh for surface marks, since another part of that mesh may correctly hide the mark. Preserve the intentional host exclusion for volume fills. PBRT explains why a single large ray epsilon can remove valid nearby occlusion, and how surface error bounds support safer ray origins. [Managing Rounding Error](https://www.pbr-book.org/4ed/Shapes/Managing_Rounding_Error)

   A watertight triangle kernel is a strong follow-up for shared edges and skinny triangles. Adopt its bounding-box requirements too; replacing only the triangle formula is incomplete. The current probes demonstrate scale sensitivity, not a measured shared-edge crack rate. [Woop, Benthin and Wald, Watertight Ray/Triangle Intersection](https://jcgt.org/published/0002/01/05/)

7. **Move from sampled points to visible segment intervals.** In [projectPaths](../src/lib/projection.ts), a hidden sample ends the stroke at the previous visible sample. Boundaries are therefore quantized by world-space step. Worse, an occluder between two visible samples produces no hidden sample at all. Perspective and zoom change the projected size of the error; lowering the global step increases work everywhere.

   An immediate improvement is to bracket detected visible/hidden transitions and bisect until their projected separation is below a pixel or millimeter tolerance. This sharpens known boundaries but cannot discover an occluder between two equally visible endpoints. Testing only the midpoint has the same blind spot for smaller off-center blockers. Use conservative occluder candidates and a maximum projected subdivision size alongside refinement, and describe that mode as approximate.

   The stronger export algorithm is segment/triangle visibility clipping. For each projected line segment, find overlapping projected triangles through a spatial index, compute overlap parameter intervals, compare line and triangle depth over those intervals, split at depth crossings, union hidden intervals, and emit the complement. Perspective depth must be interpolated correctly; linear interpolation of raw world-space z in screen space is wrong. Handle near-plane clipping before perspective division, shared edges, coplanarity, and ownership of the source line. Analytic primitives can provide exact intervals where practical, or be tessellated to a stated projected error tolerance. This provides continuous vector boundaries for the represented geometry; arbitrary tessellated curves are still approximations.

   I would implement this first for triangle meshes, extruded SVG/text, and boxes. Keep the sampled renderer as a preview/fallback while comparing outputs. A raster depth buffer can accelerate preview or candidate rejection, but finite depth-buffer resolution alone should not define plot-ready SVG visibility: small holes and thin blockers can disappear.

8. **Give height fields a representation/error contract.** The custom [HeightField](../src/lib/height-field.ts) correctly replaces several broken upstream `Function` behaviors, but its 128-step sign scan accepts only `before * after < 0`. It misses roots at sample or box boundaries, tangencies, and potentially multiple crossings between samples. It has an independent ray-distance ceiling of 1e6. Its displayed 64-division grid and analytic ray sampling do not share an approximation bound.

   Accept bounded endpoint roots, separate source-contact rejection from root existence, and test flat surfaces and tangencies. For export, adaptive tessellation shared by paths and occlusion offers a consistent geometric representation. Arbitrary expressions cannot be guaranteed by sign sampling alone; stronger guarantees require bounds on the function or a declared tessellation tolerance.

9. **Patch vector math, but keep its current impact in perspective.** [Vector.lengthSquared](https://github.com/aweary/ln.js/blob/97ea438db32a307519457f03101a393568dc11a5/src/vector.ts) computes `x*x + y*y + z + z`. Fix to `z*z` and cover segment-distance calculations. Upstream simplification depends on this helper, but the app bypasses that simplifier and the normal post-projection paths have z=0. This is a real fork bug, not the primary explanation for current viewport occlusion.

10. **Add bounded any-hit queries before replacing the tree.** [Scene.visible](https://github.com/aweary/ln.js/blob/97ea438db32a307519457f03101a393568dc11a5/src/scene.ts) requests a nearest intersection, even though it only needs to know whether any blocker exists before the camera boundary. Add `occluded(ray, tMin, tMax, filter)` throughout the tree and primitive APIs. Clip the root and child intervals to the query, terminate at the first accepted blocker, and avoid allocating full hit objects for rejected candidates. Keep closest-hit and all-crossings APIs for callers that need them. This distinction is also explicit in PBRT’s `Intersect` versus `IntersectP` interface. [Primitive Interface](https://pbr-book.org/4ed/Primitives_and_Intersection_Acceleration/Primitive_Interface_and_Geometric_Primitives)

   The harness measured seven primitive calls for seven shapes entirely beyond the eye. A bounded root-box query can skip them all. This is an operation-count result, not a claimed application-wide speedup.

Additional code-level opportunities, not yet benchmarked:

- The upstream tree is a spatial kd-tree, with shape references duplicated across split planes. It tries median bound coordinates and a count-based split score, and retains shape arrays in internal nodes. Measure duplicate references, node visits, build time, and memory before adopting a binned surface-area-heuristic BVH. The app’s separate fill BVH uses centroid median splits and gathers/sorts all hits; it should not be substituted unchanged for an any-hit renderer.
- Introduce one world-space scene hierarchy over instances and reusable local-space mesh hierarchies. Transform-only edits can update instance bounds without rebuilding every mesh. Correct transformed ray distances are a prerequisite.
- Scene preparation builds a separate scene tree per fill batch, and surface fills create deep-copied host meshes. Replace these exclusions with explicit owner/primitive filters on shared acceleration data where semantics match. Keep distinct volume-fill and surface-fill rules. Existing caches already make camera-only motion cheaper; the additional opportunity is rebuild/memory cost for edits and many fills.
- Shared mesh edges are emitted once per triangle by `Mesh.paths`. Deduplicate edges and distinguish boundary, crease, silhouette, and triangulation edges before occlusion. This can reduce both query count and duplicate pen strokes. It does not by itself repair missing visibility.
- Adjacent segments resample shared endpoints. Reuse their visibility results, and consider testing the previous blocker first for neighboring samples. Check the full spatial index when that blocker misses. Benchmark allocations and ray counts before moving all geometry to typed arrays or WASM.
- Upstream `Path.filterPaths` repeatedly concatenates arrays, and its clip filter tests sampled points after projection. These deserve fixes in a general fork, but the app already uses its own streaming projection and homogeneous segment clipping. Replacing those app improvements with the upstream render path would regress behavior.
- Upstream `Function.contains` assigns rather than compares its direction, and its intersection marcher has a hard-coded distance limit. The app bypasses it with `HeightField`; preserve that separation during migration.

A practical patch sequence is:

| Stage | Deliverable | Acceptance evidence |
|---|---|---|
| 1 | Small maintained fork with unchanged public imports; fix transform distances, parallel slabs, primitive caps, vector math, and immediate CSG defects | Convert corresponding diagnostic cases to passing assertions; compare transformed instances to equivalent baked geometry |
| 2 | App camera-aware bounded visibility; numerical/source-contact policy; endpoint-safe height fields | Perspective and orthographic fixtures, scale sweeps, coplanar contacts, boundary roots, near-plane policy tests |
| 3 | Bounded any-hit traversal and shared fill acceleration | Identical visibility decisions; fewer primitive tests, measured build time and heap cost on dense grids and text |
| 4 | Projected-tolerance refinement for preview | Zoom and resolution sweeps; measured endpoint error and a documented minimum detectable feature size |
| 5 | Segment interval clipping for final SVG | Thin blockers and slits resolved without global oversampling; analytic/reference interval comparisons; no reconnection across hidden intervals |
| 6 | Instancing, improved BVH builds, mesh feature edges, optional accelerated preview | Representative latency, memory, path count, and pen-travel measurements; retain deterministic CPU export |

For the fork, start with the verified upstream commit and retain a clear patch history. Keep the app’s `@lnjs/core` import boundary, using a pinned local package or package alias during development, then a reproducible published version or pinned build artifact. Do not edit `node_modules` as the implementation. Keep app camera policy and SVG quality controls outside the geometry dependency. The current published package and repository have different version numbers despite matching sources, so verify built entry points and types when packaging. This review did not create a remote fork or publish a package.

The controls should express output quality and drawing intent rather than expose arbitrary internal steps:

| Control | Meaning |
|---|---|
| Visibility quality | Fast preview, refined preview, or vector export; make approximation limits clear |
| Boundary tolerance | Pixels in preview; millimeters on the exported page, separate from curve-flattening tolerance |
| Occlusion participation | Independently choose whether a layer draws paths, blocks other layers, or receives occlusion |
| Surface behavior | Closed solid or open surface where the primitive supports both |
| Edge selection | Boundary, crease angle, silhouette, or all mesh edges |
| Hidden-line style | Remove, dash, or place hidden intervals on another pen/layer |

Keep numerical ray bias internal by default. A user-facing “fix artifacts” epsilon slider would hide inconsistencies instead of establishing reliable geometry.

Validation should include analytic boxes/spheres; scaled instances versus baked meshes; axis-parallel and split-plane rays; rays on faces/edges/vertices; tiny and large geometry; camera-inside cases; all supported CSG operations; thin blockers and slits smaller than the old step; concave surface fills versus intentional volume fills; and near-plane crossings. Use brute-force primitive traversal as a tree oracle, but remember it cannot detect a primitive bug shared by both paths. For visibility quality, compare analytic intervals or independently validated fixtures, not only a smaller sampling step.

Measure scene construction and projection separately, then report p50/p95 render latency, primitive tests, node visits, samples, peak memory, SVG path/vertex counts, and projected endpoint error. Include dense cube grids, extruded text, high-triangle imported meshes, and many-fill scenes, with fixed seeds and camera sequences. No representative wall-clock benchmark or interactive visual corpus was run in this review, so a numeric speedup estimate would be premature.

My recommendation is to proceed with the fork and stages 1–3 first. They address proven errors and unnecessary work while preserving the app’s current architecture. Stage 5 is the larger investment that can substantially improve the precision of the final plotted linework.
